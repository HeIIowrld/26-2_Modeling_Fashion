# 의류 속성 분류 모델 개선 — 발표 요약

> 상세 내용: [FINAL_REPORT.md](FINAL_REPORT.md)

---

## 1. 한 줄 결론

> **12개 학습 설정을 3개 시드로 총 36회 학습해도 성능은 오르지 않았고,
> 데이터를 4.7배로 늘리자 macro-F1이 6.7pt 올랐다.**
>
> 병목은 모델이 아니라 **라벨당 학습 표본 수**였다.

---

## 2. 무엇을 다루는 모델인가

- FashionSigLIP(고정) 위에 얹은 **17개 속성 분류 헤드** — 이 레포에서 유일하게 학습되는 모델
- 카테고리 / 소매 / 기장 / 넥라인 / 칼라 / 핏 / 실루엣 / 패턴 / 소재 / 디테일 등 **124개 라벨**
- 백본은 freeze → 임베딩 캐시 위에서만 학습하므로 **CPU로 수 분이면 재학습** 가능

---

## 3. 최종 성과

| 지표 | 기존 배포 모델 | **개선 모델** | 변화 |
|---|---|---|---|
| mean score | 0.7482 | **0.7641** | **+1.6pt** |
| **mean macro-F1** | 0.6054 | **0.6726** | **+6.7pt** |
| 학습 crop | 4,789 | **22,341** | 4.7배 |

*(기존 validation set 1,195 crop 기준. 17개 태스크 중 10개 상승)*

표본이 더 많은 **새 validation set 1,716 crop**에서는 차이가 더 큽니다 — **13개 태스크 전부 상승**:

| 지표 | 기존 | **개선** | 변화 |
|---|---|---|---|
| mean score | 0.7090 | **0.7651** | **+5.6pt** |
| mean macro-F1 | 0.5337 | **0.6785** | **+14.5pt** |

> **macro-F1을 강조하는 이유**: 기존 지표(accuracy·micro-F1)는 다수 라벨에 끌려가
> 소수 라벨이 완전히 죽어 있어도 좋아 보입니다. 예를 들어 `pattern`은 micro-F1 0.884였지만
> `그래픽`·`애니멀`의 F1은 **0.000**이었습니다. macro-F1은 이걸 드러냅니다.

## 4. 과정 요약 (3단계)

### ① 진단 — 무엇이 문제였나

- **과적합**: train 0.908 vs val 0.748
- **죽은 라벨 20개**: 학습 표본 30장 미만 라벨은 거의 전부 F1 < 0.40, 상당수 0.000
- **오답의 37.3%가 인접 라벨 혼동** (크롭↔기본 기장, 슬림↔레귤러핏 등)
- **평가 방식 문제**: 원본 코드가 val 셋으로 early stopping과 성능 보고를 동시에 수행
  → 프로토콜을 고쳐 재측정한 결과 누출 크기는 0.23pt로 작았습니다

### ② 학습 방법 개선 시도 → **실패**

dropout, weight decay, mixup, 임베딩 노이즈, focal loss, 라벨 스무딩, 클래스 가중치,
헤드 용량(64/128/256)을 조합해 **12개 학습 설정을 3개 시드로 총 36회 학습**하며 탐색.

**결과: 어떤 조합도 기존 설정을 넘지 못했습니다.** (최선 0.7422 vs 기존 0.7482)

이유는 **제로섬**이었습니다 — 규제를 세게 걸면 약한 태스크가 조금 오르고 강한 태스크가 그만큼 내려갑니다.
라벨 수정도 15회 더 시도했지만 트레이드오프에 그쳤습니다.

### ③ 데이터 보강 → **성공**

기존 코드가 Fashionpedia의 **검증 split 1,158장만** 쓰고 있었고,
**train split 45,623장**이 같은 라이선스·같은 주석 체계로 남아 있는 것을 발견했습니다.

| | 방법 |
|---|---|
| 문제 | 주석 542MB, 가용 메모리 1GB 미만 → 통째로 못 읽음 |
| 해결 | **ijson 스트리밍**으로 333,401개 주석을 훑어 이미지별 라벨 집합만 추출 |
| 문제 | CPU 임베딩 2.2 crop/s → 45,623장 전량은 비현실적 |
| 해결 | **탐욕적 집합 커버**로 "부족한 라벨을 가장 많이 채워주는" 10,500장만 선택 |

2회에 걸쳐 crop 19,268개를 추가 (임베딩 총 143분).

## 6. 신뢰성 검증

| 검증 항목 | 결과 |
|---|---|
| 학습셋 ↔ 평가셋 **이미지 중복** | **0건** (사진 1장에서 crop이 여러 개 나오므로 이미지 단위로 전수 검사) |
| 기존 배포 모델 파일 | **변경 없음** (sha256 확인) |
| 최종 모델 포맷 호환 | 기존 로더로 **정상 로드 확인** |

**용어 주의**: 이 작업의 평가셋은 모두 **validation set**입니다. 완전히 독립된 test set은
확보하지 않았습니다 — 새 평가셋도 2차 보강 설계 시 1차 결과를 참고했기 때문입니다.

**두 평가셋의 성격이 다릅니다.** 기존 validation set(1,195)은 **기존 데이터 구성에 상대적으로
가까운 분포지만 실사용 분포를 대표하지는 않으며**, 희소 라벨 표본이 4~20장 수준이라 라벨별
지표 변동이 큽니다. 새 validation set(1,716)은 표본이 충분하지만 **희소 라벨이 많이 들어가도록
선별한 데이터라 실제 라벨 분포를 더 크게 벗어납니다.**
**어느 쪽도 전체 점수를 실사용 기대 성능으로 읽으면 안 됩니다.**

*(발견한 문제 1건: 학습 내부의 fit/dev 분할이 crop 단위여서 dev의 60%가 fit과 이미지를 공유합니다.
dev는 early stopping에만 쓰였고 위 성능 수치에는 영향이 없지만, 다음 작업에서 수정이 필요합니다.)*

## 7. 남은 한계

1. **하의 세부 4축(`lower_subtype` `pant_leg_shape` `pant_length` `lower_detail`)은
   이번 보강으로 직접 개선되지 않았습니다** — Fashionpedia에 해당 라벨이 없어 새 표본이
   한 건도 추가되지 않았습니다. 결과는 엇갈려서 `pant_leg_shape` **+4.0pt**,
   `lower_subtype` **+2.4pt**로 오르고 `pant_length` **−1.8pt**, `lower_detail` **−5.6pt**로
   내렸는데, **새 데이터를 받지 않은 축이므로 재학습에 따른 변동으로 봐야 합니다**
   (기장 태스크인 `lower_length` −3.3pt는 이 4축과 별개이며, Fashionpedia에 라벨이 있어
   표본을 실제로 받았습니다)
2. **약지도 라벨 노이즈** — 학습 데이터 상당수가 상품명 파싱 결과라 정답 자체가 의심스러운 경우 존재
3. **인접 라벨 혼동은 그대로** — 오답의 37.3%, 데이터로도 풀리지 않음
4. Fashionpedia train split의 **23%만 사용** (45,623장 중 10,500장)
5. 실제 한국 사용자 전신사진에 대한 검증 없음 (학습 데이터는 쇼핑몰 상품컷)

## 8. 다음에 할 일 (비용 대비 효과 순)

**모델 성능 개선**

| 우선순위 | 조치 | 기대효과 | 비용 |
|---|---|---|---|
| **1** | Fashion200K 하의 데이터 보강 | 이번에 직접 보강되지 않은 유일한 영역 | 반나절 |
| 2 | 약지도 라벨 200~300장 사람 재검수 | **달성 가능한 상한선 확정** | 반나절 |
| 3 | Fashionpedia 3차 보강 | 아직 포화되지 않음 | 임베딩 ~3시간 |
| 4 | FashionSigLIP 부분 미세조정 | 국소 디테일 한계 돌파 | GPU 필요 |

**별도 트랙 — 표본 부족 라벨 차단 기준 5 → 30 (추론 정책, 모델 개선 아님)**

이건 모델 성능을 올리는 게 아니라 **coverage-accuracy 트레이드오프**입니다.
신뢰할 수 없는 세부 라벨을 내놓지 않으므로 **출력된 답의 정확도는 오르지만,
그만큼 응답률이 떨어져 `분석 보류`가 늘어납니다.** 모델 가중치는 바뀌지 않습니다.
"틀린 답과 무응답 중 무엇이 더 나쁜가"에 대한 제품 판단입니다.

**별도 트랙 — 라벨 스키마 통합 (제품 결정, 모델 개선 아님)**

크롭 기장과 기본 기장을 합치면 `upper_length`가 0.811 → 1.000이 됩니다.
**하지만 이건 모델이 사진을 더 잘 보게 된 게 아니라, 구분이 어려운 두 라벨을 합쳐
문제를 쉽게 만든 것입니다.** 사용자에게 주는 정보의 세밀도가 줄어드는 대가가 있습니다.

판단 기준은 성능 수치가 아니라 **"추천 로직에 이 구분이 실제로 필요한가"**이며,
위 모델 개선 항목과는 분리해서 논의해야 합니다.
