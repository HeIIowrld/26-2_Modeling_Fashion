## 0. 30초 요약 (질문받으면 이렇게)

**FITTA는 전신 사진 한 장에서 체형과 착장을 읽어, 규칙 기반 점수로 코디를 추천하고, 추천한 옷을 입은 모습까지 생성해 보여주는 시스템이다.**

- 사진 → 정보 추출에 **컴퓨터 비전 모델 4종**을 쓴다. 그중 **직접 학습시킨 것은 1개**(의류 속성 분류 헤드)이고 나머지 3개는 사전학습 모델을 그대로 쓴다.
- 추천은 딥러닝이 아니라 **패션 규칙 55개(그중 48개 실행)**를 점수화한 규칙 엔진이다. 학습 없음.
- 학습 실험의 핵심 결론: **레시피를 51번 바꿔도 성능이 안 올랐고, 데이터를 4.7배로 늘리자 macro-F1이 6.7pt 올랐다.** 병목은 학습법이 아니라 라벨당 표본 수였다.

## 2. 전체 파이프라인 — 사진 한 장이 추천이 되기까지

```
사용자 전신사진 (JPG/PNG/WEBP, 최대 12MB)
  │
  ├─ ① 입력 품질 검사      quality_checker      전신이 다 나왔는지, 관절이 보이는지
  │
  ├─ ② 자세 추정          MediaPipe Pose       관절 33점 → 어깨·골반·다리 비율
  │      └─ 체형 판정      body_shape.py        역삼각·사각·삼각 (실측 입력 시 6분류)
  │
  ├─ ③ 의류 영역 분리      FASHN Human Parser   픽셀 단위 18개 부위 라벨
  │      └─ crop 생성      상의/하의 영역만 잘라냄
  │
  ├─ ④ 속성 인식          FashionSigLIP + 학습 헤드 17개   ★ 유일하게 학습시킨 부분
  │      ├─ 보조: 소매 걷음 검증   wear_state_analyzer
  │      └─ 보조: 레이어드 판정    layering_model
  │
  ├─ ⑤ 추천 생성          recommendation_engine   규칙 55개 → 점수 → 상위 3벌
  │      └─ 키워드 생성    recommendation_keywords → 무신사 실시간 검색
  │
  └─ ⑥ 가상 피팅          CatVTON (확산 모델)   GPU 필요, 학교 서버에서 실행
```

**단계 이름은 코드에 그대로 있다** — `web/pipeline.py:77`의 `STAGES` 리스트: `quality` → `pose` → `outfit` → `recommend` → `preview`.

## 2+. 우리가 쓴 CV 기술

"어떤 컴퓨터 비전 기술을 썼나"라는 질문에 이 표 하나로 답할 수 있다.

| 기술 분야 | 어디에 썼나 | 쓴 모델·방법 | 우리가 학습? |
|---|---|---|---|
| **자세 추정** `Pose Estimation` | 관절 33곳 좌표를 찾아 체형 비율 계산 | MediaPipe Pose (BlazePose 계열) · 2D + 3D world | 아니오 |
| **의미론적 분할** `Semantic Segmentation` | 픽셀마다 상의·하의·배경 등 18개 부위로 분류 | FASHN Human Parser | 아니오 |
| **비전-언어 임베딩** `Vision-Language Embedding` | 옷 이미지를 768차원 벡터로 변환 | FashionSigLIP (CLIP 계열) · `open_clip` | 아니오 (동결) |
| **다중 레이블 분류** `Multi-label Classification` | 임베딩에서 17가지 특징을 동시에 판정 | MLP 헤드 17개 — 직접 설계·학습 | **예** |
| **제로샷 분류** `Zero-shot Classification` | 학습 헤드가 없는 속성을 텍스트 유사도로 판정 | FashionSigLIP 이미지–텍스트 유사도 | 아니오 |
| **이미지 생성** `Diffusion / Virtual Try-On` | 추천한 옷을 입은 모습을 새로 그림 | CatVTON (SD Inpainting 기반) | 아니오 (추론만) |
| **기하 기반 마스킹** `Geometric Masking` | 합성할 옷 영역 마스크를 관절 + 파싱으로 생성 | OpenCV · 자체 구현 | 해당 없음 |
| **색 공간 변환** `Color Quantization` | 옷 영역의 대표 색을 색 이름으로 변환 | RGB→LAB 후 대표값과 거리 비교 | 아니오 |

> **한 문장으로**: 사전학습 모델 **세 종류**(자세 추정 · 영역 분할 · 비전-언어 임베딩)를 조합해 사진에서 정보를 뽑고, 그 위에 **우리가 설계·학습한 분류 헤드 17개**를 얹었으며, 결과를 보여주는 데 **생성 모델**을 쓴다.

### 왜 이 조합인가

- **백본을 왜 CLIP 계열로 골랐나** — 이미지와 텍스트가 같은 벡터 공간에 있어서, 학습 데이터가 없는 속성도 프롬프트만으로 판정할 수 있다(제로샷). 학습 헤드가 있는 17개와 없는 속성을 **같은 임베딩 하나로** 처리한다.
- **왜 분할이 따로 필요한가** — 자세 추정만으로는 옷의 색·소재를 알 수 없다. 픽셀 단위로 옷 영역을 떼어내야 배경색에 오염되지 않은 색을 뽑는다.
- **왜 헤드만 학습했나** — GPU가 없었다. 백본을 얼리면 임베딩을 한 번만 계산해 캐시로 두고 그 위에서만 학습하므로 CPU로 몇 분이면 끝난다.

## 3. 모델별 상세 — "어디서 가져와서 어떻게 썼나"

### ③-0. 먼저 — 백본과 헤드가 무엇인가

**backbone**은 원래 **척추·등뼈**를 뜻한다. 딥러닝에서는 **입력에서 특징을 뽑아내는 신경망의 앞부분**을 가리키는 표준 용어로 굳었다. 뒤에 붙는 과제별 부분을 떠받친다는 의미다.

| 부분 | 역할 | 우리 프로젝트에서 | 파라미터 |
|---|---|---|---|
| **백본** `backbone` | 특징 추출기 — 사진을 숫자 벡터로 | Marqo fashionSigLIP · 옷 사진 → 768차원 | 203,155,970 |
| **넥** `neck` | 특징 통합기 — 여러 크기의 특징을 섞음 | **없음** — 벡터 하나를 그대로 넘김 | — |
| **헤드** `head` | 예측기 — 벡터를 읽고 답을 고름 | 분류 헤드 17개 | 3,404,668 |

객체 탐지 연구에서 `backbone → neck → head`로 나눠 부르던 관습이 표준이 됐다. 우리는 neck이 없다. 백본이 이미 벡터 하나로 압축해 주기 때문이다.

#### 768차원 벡터 하나를 17개 헤드가 나눠 쓴다

```
옷 사진 1장
   └─ 백본 1번 통과  →  768개 숫자 (딱 하나)
        ├─ [헤드 01 category]    →  상의 / 하의 / 원피스 …  (18가지 중 1개)
        ├─ [헤드 02 neckline]    →  라운드 / 브이넥 / 터틀넥 …
        ├─ [헤드 03 material]    →  데님 / 니트 / 코튼 …
        │      ⋮
        └─ [헤드 17 silhouette]  →  A라인 / H라인 …
```

17개 헤드는 **서로 완전히 독립**이다. 넥라인 헤드가 낸 답이 소재 헤드에 영향을 주지 않는다. 헤드 하나의 실제 구조는 이렇다 (`category` 기준).

```
LayerNorm(768)         768개 값을 정규화
Linear(768 → 256)      196,864 파라미터
GELU + Dropout
Linear(256 → 18)         4,626 파라미터   ← 답이 18가지
```

> ⚠️ **코드에는 다른 길도 있다.** 속성별로 전처리를 달리하는 라우팅 표가 있다. 기장·핏·실루엣 8개는 `letterbox`(비율 유지), 넥라인·패턴·소재 9개는 `squash`(눌러서 비율 제거)를 쓰도록 돼 있다. 이 방식을 쓰면 같은 사진을 두 가지로 전처리해 백본을 **두 번** 통과시킨다. 다만 **현재 배포 체크포인트는 이걸 쓰지 않는다** — `preprocessing: None` 이라 17개 모두 같은 벡터 하나를 받는다.

#### 왜 백본 구조를 바꾸지 않고 헤드만 붙였나

| # | 이유 | 내용 |
|---|---|---|
| ① | 백본의 가치는 구조가 아니라 **학습된 가중치** | 구조를 바꾸면 기존 가중치의 모양이 안 맞아 하나도 못 쓴다. 수억 장으로 처음부터 다시 학습해야 한다 |
| ② | 데이터 규모가 안 맞음 | 백본은 수억 장, 우리는 22,341 crop. 2억 파라미터 구조를 재설계할 양이 아니다 |
| ③ | 17개 과제가 **백본 통과 1번**을 나눠 씀 | 과제마다 백본을 뒀다면 34억 파라미터에 사진당 17번 통과. "소매가 길다"와 "카키색이다"에 필요한 시각 정보는 상당 부분 겹친다 |
| ④ | 헤드는 **떼었다 붙일 수 있음** | 파라미터를 공유하지 않아 과제마다 다른 시드의 헤드를 골라 조립할 수 있었다 (4-7 참조) |

백본을 건드리는 방법이 없지는 않다. 다만 **구조를 바꾸는 게 아니라 살짝 열거나 끼워 넣는** 방식이다.

| 방법 | 무엇을 하나 | 사전학습 보존 |
|---|---|---|
| 부분 해동 | 마지막 2~4개 블록만 업데이트 허용 | 대부분 유지 |
| LoRA · 어댑터 | 기존 층 사이에 작은 학습 모듈을 끼움 | 원본 가중치 그대로 |
| 전체 파인튜닝 | 2억 개를 모두 업데이트 | 유지되지만 망가질 위험 |
| 구조 변경 | 층 수·차원을 바꿈 | **전부 버림** |

> **이 판단이 맞았다는 증거**: 헤드의 중간층을 256 → 128 → 64로 **줄여도** 성능이 떨어지지 않았다. 표현력이 남아돌았다는 뜻이고, **백본이 이미 필요한 정보를 다 담아주고 있었다**는 뜻이다.

#### 임베딩을 캐시로 저장한다는 것

백본이 동결이면 **같은 사진은 항상 같은 768개 숫자**를 낸다. 그런데 학습은 데이터를 100번 반복해서 본다. 캐시가 없으면 똑같은 계산을 100번 하게 된다.

```
[캐시 없이]  에폭마다  사진 → 백본(2억) → 숫자 → 헤드 학습
                              ↑ 매번 같은 계산을 100번

[캐시 사용]  준비 1회  사진 → 백본(2억) → 숫자를 .pt 파일로 저장
             학습     .pt 열기 → 숫자 100번 재사용 → 헤드만 학습
```

같은 PC에서 실측한 값이다 (사진 40장 · 10 에폭).

| 방식 | 시간 |
|---|---|
| 캐시 없이 10 에폭 | 152.2초 |
| 캐시 만들기 (1회) | 11.3초 |
| 캐시로 10 에폭 학습 | **0.03초** |

학습 부분만 보면 **5,700배** 차이다. 프로젝트에서 **임베딩 143분**이 걸렸다는 숫자가 캐시를 만든 시간이고, 덕분에 **학습 57회를 GPU 없이** 돌릴 수 있었다.

> ⚠️ **이 설계의 대가**: 캐시에는 확정된 숫자만 있어서 **이미지 단위 증강(좌우 반전·랜덤 크롭·색 지터)을 걸 수 없다.** `R2_mixup` 도 이미지가 아니라 **벡터끼리 섞는** 방식이다. GPU가 생기면 이 맞바꿈을 뒤집을 수 있다.


### ③-1. MediaPipe Pose — 자세 추정

| 항목 | 내용 |
|---|---|
| 출처 | Google MediaPipe (pip 패키지, 사전학습) |
| 학습 여부 | **안 함.** 그대로 사용 |
| 설정 | `model_complexity=1`, `enable_segmentation=True` (`pose_analyzer.py:93`) |
| 출력 | 관절 33점의 x·y·z 좌표 + 사람 실루엣 마스크 |
| 우리가 계산하는 것 | 어깨:골반 비율, 상체:하체 비율, 다리 길이 비율 |
| 주의 | **파이썬 3.13에서 동작하지 않는다.** 3.9~3.12 필요 |

**왜 이걸 골랐나**: 별도 라이선스 동의나 모델 다운로드 없이 CPU에서 즉시 돌아간다. 3D world 좌표를 제공해서 카메라 각도에 덜 민감하다.

**한계 (반드시 알고 있을 것)**: 여기서 나오는 값은 **실제 신체 치수가 아니라 사진 안에서의 상대 비율**이다. 줄자로 잰 값과 비교 검증한 적이 **없다**. `config.py`에도 주석으로 명시돼 있다.

### ③-2. 체형 분류

- 사진에서는 **둘레를 잴 수 없어** 어깨·골반 폭만으로 역삼각·사각·삼각 3가지만 구분한다 (`body_shape.py:3`).
- 사용자가 쓰리사이즈를 입력하면 모래시계·마름모꼴·둥근체형까지 6분류가 된다.

#### 신뢰도는 무엇을 재는 값인가

`body_shape_confidence`는 **네 항목의 가중 평균**이다 (`pose_analyzer.py:258`).

```
body_shape_confidence
    = 0.45 × mean_visibility    관절이 얼마나 잘 보이나
    + 0.25 × front_score        얼마나 정면인가
    + 0.20 × full_body_score    전신이 다 나왔나
    + 0.10 × margin_score       분류 경계에서 얼마나 떨어져 있나
```

| 항목 | 계산 | 언제 떨어지나 |
|---|---|---|
| `mean_visibility` | MediaPipe가 관절마다 내놓는 visibility 값의 **평균** | 옷·물체에 가려질 때 |
| `front_score` | `1 − max(어깨기울기/0.12, 몸통기울기/0.16)`, 0~1로 자름 | 옆으로 서거나 몸이 기울 때 |
| `full_body_score` | `0.50×보이는관절비율 + 0.30×평균visibility + 0.10×발끝포함 + 0.10×머리포함` | 발끝·머리가 잘렸을 때 |
| `margin_score` | `shoulder_hip_ratio`가 분류 경계에서 떨어진 거리 ÷ 밴드 폭 | 경계에 걸친 애매한 비율일 때 |

> ⚠️ **오해하기 쉬움**: 이 값은 **모델이 체형을 맞혔을 확률이 아니다.** 정답과 대조해 보정한 적이 없다. **"이 사진이 비율을 재기에 좋은 조건인가"를 사람이 정한 가중치로 합산한 점수**다. "신뢰도 0.65"는 체형 판정이 65% 맞다는 뜻이 아니라 **촬영 조건을 네 가지로 채점한 값**이다.

#### 0.65 미만이면

- 체형 라벨을 만들지 않고 `SHAPE_UNCERTAIN`(판정 보류)으로 둔다.
- 경고 문구를 붙인다 — "촬영 자세 또는 경계에 가까운 비율 때문에 체형 분류를 보류했습니다."
- 추천 쪽에서도 `recommendation_engine.py:597`에서 같은 0.65로 다시 거른다.

#### 분류 경계값의 출처 — 함정

경계는 코드에 박힌 절대값이 아니라 `data/body_shape_reference.json`의 **33·67 백분위**다.

| 항목 | 값 |
|---|---|
| 기준 분포 표본 | **720장** (Fashionpedia seed) |
| 필터 | 전신 인식 + 정면 + `full_body_score ≥ 0.85` |
| 33% 경계 | **1.4069** — 이하면 삼각체형 |
| 67% 경계 | **1.4574** — 초과면 역삼각체형 |

> ⚠️ **발표 표현 주의**: "Size Korea 기준"이라고만 말하면 정확하지 않다. **분류 체계**(역삼각·사각·삼각)는 Size Korea 『한국인의 표준체형』과 Rasband(1994)를 따르지만, **실제 경계 숫자는 Fashionpedia 720장의 백분위**다. 기준 파일 자체가 적어두고 있다 — "패션 모델 사진이라 일반 인구를 대표하지 않는다. **한국인 표본도 아니다.**"

한국인 표본으로 바꿀 때는 같은 필터로 `shoulder_hip_ratio`를 모아 **백분위만 갱신**하면 된다. 코드는 안 고쳐도 된다.

둘레 기반 6분류 규칙(`circumference_rules`)은 파일에 **"잠정값 — 전문가 검수 필요"**로 표시돼 있다.

1. 학습 표본이 `minimum_label_examples=5` 미만인 라벨은 로짓을 `-inf`로 **차단**
2. confidence가 임계값 미만이면 라벨을 비우고 **"분석 보류"**로 표시

## 4. 학습 실험 — 발표에서 가장 많이 질문받을 부분

> 출처: `ai_fashion_recommender/reports/FINAL_REPORT.md` (736줄)
> 환경: **CPU 전용**, Python 3.13.0, torch 2.13.0+cpu, 12코어 · 총 학습 **57회** · 임베딩 **143분**

### 4-0. 먼저 용어 두 개

#### macro-F1 이 무슨 지표인가

정확도(accuracy)는 **"전체 중 몇 개를 맞혔나"**다. 여기에는 함정이 있다. 데이터에 `반팔`이 900장, `돌만 소매`가 10장 있으면, 모델이 전부 "반팔"이라고만 답해도 정확도가 90%가 나온다. **드문 종류를 하나도 못 맞혀도 점수가 높다.**

macro-F1은 이걸 막는다. **라벨마다 F1을 따로 계산한 뒤, 표본 수와 무관하게 그냥 평균**낸다.

```
F1       = 정밀도와 재현율의 조화평균 (한쪽만 높으면 낮게 나옴)
            정밀도 = 반팔이라 답한 것 중 진짜 반팔의 비율
            재현율 = 진짜 반팔 중 반팔이라 맞힌 비율

macro-F1 = (반팔 F1 + 긴팔 F1 + 돌만 F1 + …) ÷ 라벨 수
            ↑ 900장짜리 라벨과 10장짜리 라벨을 똑같이 한 표씩 센다
```

그래서 **드문 라벨을 놓치면 macro-F1이 크게 떨어진다.** 1에 가까울수록 좋고, 우리 프로젝트에서는 0.605 → 0.673으로 올랐다.

> **왜 이 지표를 골랐나**: 원본 코드는 macro-F1을 계산하지 않았다. 그래서 **소수 라벨이 통째로 붕괴해도(F1 = 0.000) 전체 점수에는 티가 나지 않았다.** 이 지표를 도입한 것이 "병목은 데이터"라는 진단의 출발점이었다.

#### dev(개발셋)는 무엇인가

데이터를 세 덩어리로 나눈다. **각각 하는 일이 다르다.**

| 이름 | 크기 | 하는 일 | 비유 |
|---|---|---|---|
| `train_fit` | 4,071 | 모델이 실제로 보고 배우는 데이터 | 교과서 |
| `train_dev` | 718 | 언제 학습을 멈출지, 임계값을 얼마로 할지 **고르는** 데 씀 | 모의고사 |
| `val` | 1,195 | 최종 성적을 **보고**하는 데만 씀 | 수능 |

dev가 필요한 이유는 이렇다. 100 에폭을 돌리면서 "어느 시점이 가장 좋은가"를 고르려면 점수를 재야 하는데, **그 점수를 최종 보고에도 쓰면 시험 문제를 미리 본 것과 같다.** 그래서 고르는 용도와 보고하는 용도를 갈라놓는다.

> ⚠️ **원본 코드의 문제**: 원래는 **val 하나로 세 가지를 다** 하고 있었다. 학습 중단 시점도, 임계값도, 최종 성적도 같은 데이터로 정했다.

### 4-1. 평가 프로토콜을 고쳤다

원본 코드는 **val 셋 하나로 early stopping·임계값 선택·성능 보고를 전부** 하고 있었다. 그래서 train을 다시 쪼갰다.

```
train 4,789 ─┬─ train_fit  4,071  … 학습만
             └─ train_dev    718  … early stopping·임계값 선택만
val   1,195 …………………………… 성능 보고만
```

**누출 크기를 실제로 측정했다**: 기존 레시피를 새 프로토콜로 재학습한 대조군 0.7459 vs 배포 체크포인트 0.7482 → **차이 0.23pt**. 기존 숫자는 약간 낙관적이지만 신뢰할 만한 수준이었다.

### 4-2. 레시피 튜닝은 전부 실패했다 (학습 51회)

**1라운드 — 규제 방식 6종**: `R0_replica`, `R1_strongreg`, `R2_mixup`, `R3_heavy`, `R4_rare`, `R5_slow`
(dropout 0.3~0.6, weight decay 1e-4~5e-2, 노이즈, mixup, focal loss, 라벨 스무딩, 클래스 가중치 지수 조합)

**2라운드 — 헤드 용량 6종**: hidden_dim 64 / 128 교차 (0.9M / 1.8M 파라미터)

**12개 설정 × 3 시드 = 36회**, 여기에 라벨 수정 실험 5종 × 3 시드 = 15회 → **총 51회**

| 모델 | mean score | mean macro-F1 |
|---|---|---|
| 배포 체크포인트 | **0.7482** | 0.6054 |
| 누출 없는 프로토콜 대조군 (V0) | 0.7459 | 0.6033 |
| 최적 단일 레시피 refit (V1) | 0.7430 | 0.6049 |
| 태스크별 최적 조립 refit (V2) | 0.7422 | 0.6053 |

**왜 아무리 바꿔도 제자리였나** — "규제를 건다"는 것은 모델이 흔한 답에만 쏠리지 않게 **일부러 방해하는 것**이다. 방해를 세게 하면 모델이 드문 라벨도 답하기 시작한다. 그런데 그만큼 **잘 맞히던 흔한 라벨을 틀린다.**

실제로 약한 항목(`neckline` +3.5, `collar` +2.3)이 오른 만큼 강한 항목(`silhouette` −4.0, `pattern` −2.9)이 내려갔다. **이불이 짧아서 발을 덮으면 어깨가 나오는 상황**이다. 총합은 그대로였다.

모델 크기도 줄여봤다. 헤드의 중간층을 256 → 128 → 64로 낮췄지만 dev 점수가 오르지 않았다. **과적합은 실제로 있었지만 모델을 줄이는 것으로는 해결되지 않았다** — 이불 자체가 짧았기 때문이다.

### 4-3. 병목이 데이터라고 판단한 근거 4가지

### 4-7. 3개 시드를 하나의 체크포인트로 합친 방법

**앙상블이 아니라 태스크 단위 조립이다.** 17개 헤드가 파라미터를 공유하지 않기 때문에 가능하다.

1. 시드 0·1·2로 전체 모델을 **3번 독립 학습**
2. 에폭마다 train_dev 점수를 재고, 태스크별 최고 시점의 헤드 가중치를 스냅샷
   (선택 점수 = `0.5 × 대표지표 + 0.5 × macro-F1`)
3. 태스크마다 3개 시드 중 dev 점수가 가장 높은 시드의 스냅샷 선택
4. 17개를 조립해 하나의 체크포인트로 저장 — 기존 포맷과 100% 호환

**실제 선택 분포: 시드 1이 10개, 시드 2가 5개, 시드 0이 2개 태스크.**

최종 레시피: `R2_mixup` — dropout 0.4, weight_decay 1e-3, lr 5e-4 cosine, mixup α 0.4, batch 256, 100 epoch

### 4-8. 3차 보강은 **미채택**

`reports/ROUND3_FINAL_REPORT.md`에 기록. 기존 validation에서 하락, 새 validation에서만 상승해 **채택하지 않았다**. 이주아 님이 파이프라인을 만들었고 결과는 남겨뒀다. "왜 안 썼냐"고 물으면 이 리포트를 근거로 답하면 된다.

### 5-3. 점수 배점 (100점)

현재 착장 평가 기준 `CURRENT_OUTFIT_WEIGHTS`:

| 평가축 | 배점 |
|---|---|
| 실루엣·체형 보완 | **30** |
| 스타일링 의도·완성도 | 20 |
| 목적·TPO 적합도 | 15 |
| 색상 조화 | 15 |
| 패턴·소재·디테일 위계 | 10 |
| 사용자 취향 일치 | 10 |

#### 그래서 이 사진은 몇 점인가 — 점수를 매기는 방법

배점은 **"이 축이 총점에서 차지하는 비중"**일 뿐이다. 실제 점수는 세 단계로 만들어진다.

```
1단계  각 축이 0 ~ 1 사이의 값을 낸다
2단계  그 값에 배점(가중치)을 곱해 더한다
3단계  가중치 합으로 나누고 100을 곱한다   →   최종 점수

총점 = Σ(축 점수 × 배점) ÷ Σ(배점) × 100
```

핵심은 **1단계에서 0~1 값이 어떻게 나오는가**다. 실루엣 축(`_silhouette_score`)은 **여러 개의 작은 판정을 각각 점수화한 뒤 가중평균**한다.

| 판정 항목 | 조건 | 점수 | 비중 |
|---|---|---|---|
| **핏 조합** | 상·하의 둘 다 볼륨이 큼 | 0.48 | 0.55 |
| | 한쪽만 크고 다른 쪽은 정돈됨 | 1.00 | |
| | 그 외 | 0.84 | |
| **시각적 무게** | 어두운색·무거운 소재가 양쪽에 몰림 | 0.55 | 0.45 |
| | 위아래 무게 차이가 1~2단계 | 0.95 | |
| | 그 외 | 0.84 | |
| **상의 기장** (비율 목표 선택 시) | 크롭 1.00 · 기본 0.78 · 롱 0.45 · 하이웨이스트 +0.12 | 가변 | 0.35 |
| **체형 보완** (체형이 뚜렷할 때) | 체형별로 다름 — 아래 표 | 가변 | 0.18~0.55 |
| **다리 비율** (`leg_ratio` < 0.60) | 짧은 하체 + 긴 상의 + 밀착 하의면 감점 | 가변 | 가변 |

**삼각체형**(어깨가 좁게 분석된 경우) 항목은 이렇게 갈린다.

| 상황 | 점수 | 비중 | 적용 규칙 |
|---|---|---|---|
| 몸에 붙는 상의인데 어깨 구조·포인트가 **없음** | 0.38 | 0.55 | `R-BOD-06` |
| 몸에 붙는 상의지만 어깨 구조가 **있음** | 0.68 | 0.42 | `R-BOD-06` |
| 상체에 시선이 가고 하의는 차분함 | 1.00 | 0.30 | `R-BOD-01` |
| 그 외 | 0.66 | 0.30 | `R-BOD-01` |

점수가 낮을수록 **비중이 커진다**는 점을 눈여겨볼 것. 명확한 체형–핏 충돌(0.38)은 비중을 0.55까지 올려, 다른 항목의 좋은 점수에 희석되지 않게 한다.

> **불확실하면 점수를 중앙으로 당긴다** — 사진에서 읽어낸 값이라 확신이 낮을 때는 `_shrink_to_neutral` 이 점수를 **중립값 0.5 쪽으로 수축**시킨다 (`R-DAT-01`).
> ```
> 최종점수 = 0.5 + 신뢰도 × (원점수 − 0.5)
>
> 신뢰도 1.0  →  원점수 그대로
> 신뢰도 0.5  →  0.38 이던 점수가 0.44 로 완화
> 신뢰도 0.0  →  무조건 0.5 (판단하지 않음)
> ```
> 확신이 없으면 **좋다고도 나쁘다고도 하지 않는** 설계다.

**정리** — "실루엣 30점"은 만점이 30이라는 뜻이고, 실제 획득 점수는 `(위 가중평균 0~1 값) × 30` 이다. 딥러닝이 아니라 **규칙마다 사람이 정한 숫자**이며, 그래서 어떤 규칙이 몇 점을 깎았는지 문장으로 되돌려 설명할 수 있다.

**왜 실루엣을 30점으로 올렸나 (조규홍 님 작업)**: 마른 체형에 딱 붙는 옷이 고득점되는 문제가 있었다. 패션에서 체형 보완은 단점을 가리고 장점을 부각하는 것인데 점수가 그걸 반영하지 못했다. 그래서 `R-BOD-05`(하체 비율은 상의 밑단·기장·밀착도의 조합으로 본다), `R-BOD-06`(좁은 어깨는 상의 핏과 구조를 함께 평가), `R-CMP-02`(무난함과 완성도를 같은 점수로 보지 않는다)를 추가했다.

> 상품 추천용 `BASE_WEIGHTS`는 별도다 (purpose_tpo 0.20 / silhouette 0.15 / color 0.15 / weather 0.12 / pattern 0.10 / preference 0.08). **두 배점표가 다르다는 걸 알고 있을 것** — 질문받기 좋은 지점이다.

### 5-4. 체형이 추천에 반영되는 조건

`config.ENABLE_AUTO_BODY_SHAPE = True`

원래 규칙 `R-KOR-02`는 "사용자가 목표를 선택한 경우에만 체형 규칙 적용"이었다. 원치 않는데 체형을 지적하지 않으려는 배려였다. 그런데 그 기본값에서는 **체형을 분석해 놓고 추천에 전혀 안 쓰는** 상태가 됐다. 그래서 기본값을 켜되 두 가지를 지킨다.

1. 판정 신뢰도가 낮으면(0.65 미만) 적용하지 않는다
2. 가중치를 사용자가 직접 고른 목표보다 낮게 둔다 (자동 0.18 vs 명시 0.30)

## 10. 한계 — 질문받을 것에 미리 대비

### 10-1. 성능 수치의 조건 (metrics.json의 caveat 원문)

> **기존 검증셋**: "배포 모델은 원본 학습 코드에서 이 셋으로 early stopping과 임계값을 선택했으므로 **배포 모델에 유리한 비교**다."

> **새 검증셋**: "2차 보강 설계 시 1차 결과를 참고했으므로 **완전 독립 test set이 아니다**."

**추가로 알아야 할 것**: 새 검증셋은 무작위 표본이 아니라 **희소 라벨을 많이 포함하도록 탐욕적으로 선별한** 이미지의 20%다. 라벨별 지표는 안정적이지만 **실사용 분포를 대표하지 않는다.** 예를 들어 `니트`가 실제보다 훨씬 자주 나온다.

→ **"이 점수가 실사용 성능인가?"라는 질문에는 "아니다"라고 답해야 한다.**

## 11. 예상 질문과 답변

**Q. 모델을 직접 학습시킨 게 맞나?**
백본은 학습하지 않았다. `Marqo/marqo-fashionSigLIP`을 동결하고 그 위의 **17개 분류 헤드(340만 파라미터)만** 학습시켰다. 학습 57회, 최종 학습 데이터 22,341 crop이다.

**Q. 왜 백본을 파인튜닝하지 않았나?**
CPU만 있었다. 백본을 동결하면 임베딩을 한 번만 계산해 캐시로 두고 그 위에서만 학습하므로 CPU로도 몇 분이면 끝난다. 그리고 51회 실험 결과 병목이 모델 용량이 아니라 데이터 양이었기 때문에, 백본을 풀어도 같은 문제에 부딪혔을 가능성이 높다.

**Q. 추천에 딥러닝을 안 썼나?**
안 썼다. 의도적이다. 목표가 "정확한 추천"이 아니라 **"설명 가능한 추천"**이었다. 규칙 55개에 신뢰도와 근거 수준을 매겨 문서화하고, 추천마다 적용된 규칙 번호를 함께 보여준다.

**Q. 데이터는 어디서 가져왔나? 라이선스는?**
Fashionpedia(CC BY 4.0)와 Fashion200k. 원본 이미지는 저작권 때문에 저장소에 올리지 않고 CSV만 관리한다. CatVTON은 **CC BY-NC-SA 4.0으로 비상업 전용**이라 상업화하려면 대체가 필요하다.

**Q. 성능이 얼마나 좋은가?**
macro-F1 기준 0.605 → 0.673 (기존 검증셋), 0.534 → 0.679 (새 검증셋). 다만 **두 검증셋 모두 우리에게 유리한 조건**이고 실사용 분포를 대표하지 않는다. 최종 발표 전에 학습에 안 쓴 독립 데이터로 다시 측정할 계획이다.

**Q. 왜 3차 보강은 안 썼나?**
기존 검증셋에서 하락하고 새 검증셋에서만 올라서, 개선인지 평가셋 편향인지 구분할 수 없었다. `ROUND3_FINAL_REPORT.md`에 미채택 근거를 남겼다.
